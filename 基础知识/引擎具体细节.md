scheduler的输出scheduleroutput里面包含了什么内容：

scheduled_new_reqs:第一次被调度的请求，带完整数据，包括prompt block ids token ids

scheduled_cached_reqs：decode阶段的请求，新增的block id 新token数



kv_connector_metadata:connector这一步的load/store任务打包

has_sync_kv_loads

kv_connector_block_state





get_num_new_matched_token有可能会异步查询，然后返回none，这个逻辑需要理清楚，什么时候异步



会等最慢的路径，必须所有的路径都查出来了，然后再取第一个查出来的，如果第一个查出来是0，才会用第二个

那么这里的优先级就已经固定了呀，谁是第一个是写死的。



nixl侧的scheduler也有一个get_num_new_matched_tokens的函数，通过prefill传过来的kv_transfer_params确定到底要拉多少kv过来，减去本地GPU已有的。不用lookup，直接就能知道





shceduler有两步：第一步是schedule已经在running的请求，第二步是schedule在waiting的请求

running的请求不用查cache，不用计算num_conputed_tokens

waiting的请求需要查本地prefix cache，需要查外部connector命中的cache，

running请求有抢占，waiting请求没有



所以我们做的就是如何对waiting的请求，第一次查cache的时候更快。



本地：_get_local_prefix_cache_hit

外部：get_num_new_matched_tokens

本地和外部都命中的时候，还要对比一下命中的数量，因为操作同一个block的时候会有冲突，所以要避免这种冲突。
